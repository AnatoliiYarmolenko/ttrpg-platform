1. Вступ — чим диплом відрізняється від лабораторної

У лабораторній роботі ви будували pipeline для навчального прикладу і виконували чіткі кроки з інструкції. Дипломний проект — інша ситуація: у вас реальний застосунок, власний технологічний стек, конкретні вимоги керівника і комісії, і декілька місяців роботи які потрібно організувати так, щоб код не перетворився на хаос.

1.1 Що від вас очікує комісія

Комісія на захисті оцінює не факт наявності CI/CD, а розуміння навіщо це потрібно і як це реалізовано у вашому конкретному проекті. Очікується що ви зможете:

  • пояснити що таке pipeline і які етапи він містить у вашому проекті
  • показати реальний зелений pipeline на git.ztu.edu.ua або GitHub
  • розповісти які тести написані і що вони перевіряють
  • пояснити як відбувається розгортання застосунку
  • відповісти на питання чому обрано саме такий підхід

2. Docker для дипломника

2.1 Ліцензія Docker Desktop — що треба знати

Docker Desktop (програма для Windows і macOS з графічним інтерфейсом) має кілька планів ліцензування. Для студента на особистому ноутбуці ситуація така:

Компанія < 250 осіб і < $10M доходуPersonalБезкоштовно✓ Так
Університет як організаціяPro/Team потрібенПлатно✗ Порушення
Корпоративна машина будь-якої компаніїBusiness потрібенПлатно✗ Порушення

Висновок для вас: якщо ви виконуєте диплом на власному ноутбуці — Docker Desktop Personal Plan є безкоштовним і легальним. Встановлюйте без хвилювань.

2.2 Телеметрія Docker Desktop — що збирається

Docker Desktop збирає аналітику про використання. Важливо розуміти що саме:

  • версія Docker Desktop і ОС
  • які функції використовуються (Extensions, Dev Environments тощо)
  • частота запуску і тривалість сесій
  • загальна кількість контейнерів і images (без їх вмісту)
  • НЕ збирається: вміст контейнерів, ваш код, змінні середовища, паролі

Якщо вас турбує навіть ця телеметрія — є повноцінні альтернативи.

2.3 Альтернатива 1: Docker Engine у WSL2 (рекомендовано)

Це встановлення Docker напряму всередині WSL2 (Windows Subsystem for Linux) без Docker Desktop. Це не той самий продукт — Docker Engine є повністю open source, без телеметрії Desktop-клієнта, без ліцензійних обмежень для організацій.

Крок 1: Увімкнути WSL2 (якщо ще не увімкнено)

# Виконати у PowerShell від адміністратора
wsl --install
# Команда встановлює WSL2 і Ubuntu за замовчуванням
# Після перезавантаження: відкрийте Ubuntu зі Start Menu

# Перевірити що WSL2 активний:
wsl --list --verbose
# Очікується: Ubuntu  Running  2 (версія 2 — важливо!)

Крок 2: Встановити Docker Engine всередині WSL2

# Відкрийте термінал Ubuntu (WSL2) і виконайте:

# Офіційний скрипт встановлення від Docker
# Цей скрипт автоматично визначає дистрибутив і встановлює актуальну версію
curl -fsSL https://get.docker.com | sh
# get.docker.com → офіційний скрипт Docker Inc.
# Встановлює: docker-ce, docker-ce-cli, containerd.io

# Додати поточного користувача до групи docker
# щоб не писати sudo перед кожною docker командою
sudo usermod -aG docker $USER

# Застосувати зміну групи без виходу з системи
newgrp docker

# Запустити Docker daemon (сервіс)
sudo service docker start
# або: sudo dockerd &

# Перевірка
docker run --rm hello-world
# Очікується: "Hello from Docker!"
WSL2 і автозапуск: Docker daemon у WSL2 не запускається автоматично при старті Windows (на відміну від Docker Desktop). Перед роботою потрібно виконати sudo service docker start у терміналі WSL2. Щоб автоматизувати — додайте цей рядок у ~/.bashrc або ~/.profile. 
# Автозапуск Docker при відкритті WSL2 терміналу
# Додайте у кінець файлу ~/.bashrc:
echo 'sudo service docker start > /dev/null 2>&1' >> ~/.bashrc

# Щоб sudo не питало пароль для цієї команди — додайте у sudoers:
echo "$USER ALL=(ALL) NOPASSWD: /usr/sbin/service docker start" | sudo tee /etc/sudoers.d/docker-start

2.4 Альтернатива 2: Podman

Podman — повна альтернатива Docker від Red Hat. Повністю open source (Apache 2.0), без телеметрії, без daemon (кожен контейнер — звичайний процес). Синтаксис команд майже ідентичний Docker.

# Встановлення Podman на Ubuntu/WSL2
sudo apt update
sudo apt install -y podman

# Podman сумісний з Docker синтаксисом — просто замінюєте слово:
podman run --rm hello-world       # замість: docker run --rm hello-world
podman build -t myapp .           # замість: docker build -t myapp .
podman images                     # замість: docker images

# Псевдонім для повної сумісності (якщо скрипти написані з "docker"):
echo 'alias docker=podman' >> ~/.bashrc
source ~/.bashrc
# Тепер команда "docker" насправді викликає podman
Podman у GitLab CI/CD: якщо ваш Runner використовує Podman замість Docker — у .gitlab-ci.yml нічого міняти не потрібно, бо псевдонім alias docker=podman діє і для Runner-а. Якщо Runner зареєстровано з executor: shell — все працює прозоро.

3. Адаптація pipeline під власний стек

Лабораторна робота побудована на .NET Web API + Node.js. Ваш дипломний проект, найімовірніше, використовує інший стек. У цьому розділі показано як адаптувати pipeline під найпоширеніші комбінації технологій.

3.1 Що залишається незмінним у будь-якому проекті

Незалежно від технологій — структура pipeline залишається тією самою. Змінюються тільки конкретні команди і Docker images:

# Ця структура підходить для БУДЬ-ЯКОГО проекту
# Міняйте тільки image: і команди всередині script:
stages:
  - build    # завжди: встановлення залежностей + компіляція
  - test     # завжди: запуск тестів + лінтинг
  - docker   # завжди: docker build (якщо є Dockerfile)
  - deploy   # завжди: розгортання (реальне або імітація)

variables:
  # Змінні залежать від вашого стеку — дивіться розділи нижче
  APP_NAME: "my-diploma-app"   # назва вашого застосунку

cache:
  key: "$CI_COMMIT_REF_SLUG"
  paths: []   # заповніть відповідно до вашого стеку

3.2 Стек: Python (Flask / FastAPI / Django)

# ── .gitlab-ci.yml для Python проекту ────────────────────────────────────
stages:
  - build
  - test
  - docker
  - deploy

# Кеш для pip пакетів — економить час на повторних запусках
cache:
  key: "$CI_COMMIT_REF_SLUG"
  paths:
    - .pip-cache/   # локальний кеш pip

# ── Встановлення залежностей ──────────────────────────────────────────────
python_build:
  stage: build
  image: python:3.11   # офіційний Python image з Docker Hub
                       # Версії: python:3.9, python:3.10, python:3.11, python:3.12
  tags: [student]
  variables:
    PIP_CACHE_DIR: "$CI_PROJECT_DIR/.pip-cache"   # де зберігати кеш pip
  script:
    # Оновити pip до актуальної версії
    - pip install --upgrade pip

    # Встановити залежності з requirements.txt
    # requirements.txt генерується командою: pip freeze > requirements.txt
    - pip install -r requirements.txt

    # Перевірити що застосунок імпортується без помилок
    - python -c "import app"   # замініть "app" на назву вашого модуля
  artifacts:
    paths:
      - .pip-cache/   # зберегти кеш для stage test
    expire_in: 1 hour

# ── Тестування ────────────────────────────────────────────────────────────
python_test:
  stage: test
  image: python:3.11
  tags: [student]
  variables:
    PIP_CACHE_DIR: "$CI_PROJECT_DIR/.pip-cache"
  script:
    - pip install -r requirements.txt

    # pytest — найпопулярніший фреймворк для тестування Python
    # --verbose → показати кожен тест окремо
    # --tb=short → скорочений вивід помилок (short/long/no)
    - pytest --verbose --tb=short

    # Генерація coverage звіту (потрібен пакет pytest-cov у requirements.txt)
    # --cov=. → вимірювати покриття для всіх файлів у поточній папці
    # --cov-report=term-missing → вивести у термінал які рядки не покриті
    # --cov-report=html → згенерувати HTML звіт у папці htmlcov/
    - pytest --cov=. --cov-report=term-missing --cov-report=html
  artifacts:
    paths:
      - htmlcov/   # HTML звіт покриття — завантажте і відкрийте у браузері
    expire_in: 1 day

# ── Лінтинг ──────────────────────────────────────────────────────────────
python_lint:
  stage: test
  image: python:3.11
  tags: [student]
  script:
    - pip install flake8   # інструмент статичного аналізу Python коду
    # flake8 перевіряє: синтаксис, стиль (PEP8), потенційні помилки
    # . → перевірити всі .py файли у поточній папці
    # --max-line-length=120 → дозволити рядки до 120 символів (замість 79)
    - flake8 . --max-line-length=120 --exclude=.git,__pycache__,venv
  allow_failure: true   # лінтинг не блокує pipeline поки не всі помилки виправлено

Dockerfile для Python (Flask/FastAPI)

# api/Dockerfile для Python застосунку
FROM python:3.11-slim
# python:3.11-slim → мінімальний Python image (~150MB замість ~900MB для повного)

WORKDIR /app

# Копіюємо requirements.txt ПЕРШИМ для кешування pip install
# Якщо requirements.txt не змінився → pip install береться з кешу Docker
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
# --no-cache-dir → не зберігати кеш pip всередині image (зменшує розмір)

# Копіюємо весь код
COPY . .

# Порт на якому слухає застосунок
EXPOSE 8000

# Для FastAPI (uvicorn):
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

# Для Flask:
# CMD ["python", "app.py"]
# або: CMD ["gunicorn", "-w", "4", "-b", "0.0.0.0:8000", "app:app"]

3.3 Стек: Java (Spring Boot)

# ── .gitlab-ci.yml для Spring Boot проекту (Maven) ───────────────────────
stages:
  - build
  - test
  - docker
  - deploy

cache:
  key: "$CI_COMMIT_REF_SLUG"
  paths:
    - .m2/repository/   # локальний кеш Maven репозиторію

java_build:
  stage: build
  # maven:3.9-eclipse-temurin-21 → Maven 3.9 + Java 21 LTS
  # eclipse-temurin → OpenJDK від Eclipse Foundation (безкоштовний, без Oracle ліцензії)
  image: maven:3.9-eclipse-temurin-21
  tags: [student]
  variables:
    # Зберігати Maven залежності у папці проекту для кешу
    MAVEN_OPTS: "-Dmaven.repo.local=$CI_PROJECT_DIR/.m2/repository"
  script:
    # mvn package → компілює, запускає тести, створює .jar файл
    # -DskipTests → пропустити тести на цьому етапі (тести — в окремому job)
    # -B → batch mode: без кольорового виводу і прогрес-барів (краще для CI)
    - mvn package -DskipTests -B
  artifacts:
    paths:
      - target/*.jar   # зберегти .jar файл для deploy stage
    expire_in: 1 hour

java_test:
  stage: test
  image: maven:3.9-eclipse-temurin-21
  tags: [student]
  variables:
    MAVEN_OPTS: "-Dmaven.repo.local=$CI_PROJECT_DIR/.m2/repository"
  script:
    # mvn test → компілює і запускає всі тести (JUnit)
    # Звіти тестів зберігаються у target/surefire-reports/
    - mvn test -B

    # Генерація JaCoCo coverage звіту (якщо налаштовано у pom.xml)
    - mvn jacoco:report -B
  artifacts:
    paths:
      - target/site/jacoco/   # HTML звіт покриття
    expire_in: 1 day

Dockerfile для Spring Boot

# Dockerfile для Spring Boot застосунку
FROM eclipse-temurin:21-jre-alpine AS runtime
# eclipse-temurin:21-jre-alpine → тільки JRE (не JDK), Alpine Linux
# Розмір: ~180MB замість ~400MB для повного JDK image

WORKDIR /app

# Копіюємо .jar файл зібраний у CI
# target/*.jar → Spring Boot uber-jar (містить всі залежності)
COPY target/*.jar app.jar

EXPOSE 8080

# exec форма: не запускає shell, сигнали (SIGTERM) доходять до Java процесу
ENTRYPOINT ["java", "-jar", "app.jar"]

# Для production: додайте JVM налаштування
# ENTRYPOINT ["java", "-Xmx512m", "-Xms256m", "-jar", "app.jar"]

4. Гілкова стратегія для дипломного проекту

4.1 Навіщо гілки якщо ти працюєш один

Типова помилка дипломника — робити все в одній гілці main. Проблеми що з цього виникають:

  • зламаний код потрапляє прямо в основну гілку — pipeline стає червоним
  • немає чіткого розмежування між «стабільний код» і «робота в процесі»
  • важко відстежити коли і що зламалось
  • комісія бачить брудну історію комітів у main

Гілки вирішують це навіть для одного розробника. Крім того — правильна гілкова стратегія сама по собі є демонстрацією зрілості розробника на захисті.

4.2 Рекомендована стратегія для диплому

# Структура гілок для дипломного проекту:
#
# main ────────────────────────────────────────────────────►
#   │  (тільки стабільний, протестований код)
#   │
# develop ─────────────────────────────────────────────────►
#   │  (поточна розробка, сюди йдуть merge з feature гілок)
#   │
# feature/user-auth ───────────►
# feature/payment-module ──────────────►
# fix/login-bug ──────────►
#
# Правило: в main потрапляє тільки код з develop
#          після того як pipeline зелений і все перевірено

Налаштування захисту гілки main у GitLab

Щоб випадково не запушити у main напряму — захистіть її:

  1. Відкрийте ваш проект на git.ztu.edu.ua
  2. Settings → Repository → Protected Branches
  3. Знайдіть гілку main → натисніть Protect
  4. Allowed to push: No one (або тільки Maintainers)
  5. Allowed to merge: Maintainers
Якщо ви єдиний учасник проекту — встановіть собі роль Maintainer (вона є за замовчуванням для власника проекту). Тоді ви зможете робити merge через Merge Request, але не зможете випадково зробити push напряму.

Робочий процес з гілками

# 1. Почати нову функцію — створити гілку від develop
git checkout develop
git pull origin develop
git checkout -b feature/назва-функції
# Наприклад: git checkout -b feature/user-registration

# 2. Розробка: робіть коміти у цій гілці
git add .
git commit -m "Add user registration form"
git push origin feature/user-registration

# 3. Коли функція готова — створіть Merge Request у GitLab:
#    feature/user-registration → develop
#    Pipeline запуститься автоматично при створенні MR
#    (якщо у .gitlab-ci.yml є: only: [merge_requests])

# 4. Після merge у develop — pipeline для develop запускається знову

# 5. Коли develop стабільний і готовий до "релізу" —
#    Merge Request: develop → main
#    Pipeline для main запускає deploy stage

Налаштування pipeline для гілкової стратегії

# .gitlab-ci.yml — rules замість only/except (сучасніший підхід)
stages:
  - build
  - test
  - docker
  - deploy

build_job:
  stage: build
  image: mcr.microsoft.com/dotnet/sdk:8.0
  tags: [student]
  script:
    - dotnet build
  # rules: визначають умови запуску job (замість застарілого only:)
  rules:
    # Запускати для будь-якого push у будь-яку гілку
    - if: '$CI_COMMIT_BRANCH'
      when: always

test_job:
  stage: test
  image: mcr.microsoft.com/dotnet/sdk:8.0
  tags: [student]
  script:
    - dotnet test
  rules:
    # Запускати для будь-якого push і для merge request
    - if: '$CI_COMMIT_BRANCH'
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'

deploy_job:
  stage: deploy
  tags: [student]
  script:
    - echo "Deploying..."
  rules:
    # Запускати ТІЛЬКИ для гілки main
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: always

5.2 GitHub Actions — базовий pipeline

Файл розміщується у .github/workflows/ci.yml у корені репозиторію. GitHub автоматично виявляє його і запускає pipeline без будь-яких додаткових налаштувань.

# .github/workflows/ci.yml
# GitHub Actions pipeline — аналог .gitlab-ci.yml

# Назва workflow — відображається у GitHub → Actions вкладка
name: CI/CD Pipeline

# on: визначає коли запускати pipeline (аналог only: у GitLab)
on:
  push:
    branches: [main, develop]   # при push у ці гілки
  pull_request:
    branches: [main]            # при створенні PR у main

# jobs: аналог jobs у GitLab CI
# На відміну від GitLab — немає явного поняття stages
# Порядок визначається через needs: (залежності між jobs)
jobs:

  # ── Job: build ──────────────────────────────────────────────────────────
  build:
    # runs-on: на якій машині виконувати
    # ubuntu-latest → безкоштовна Ubuntu VM від GitHub (2 CPU, 7GB RAM)
    # Альтернативи: windows-latest, macos-latest
    runs-on: ubuntu-latest

    steps:
      # actions/checkout → клонує ваш репозиторій всередину runner
      # БЕЗ цього кроку — репозиторій недоступний!
      - name: Checkout code
        uses: actions/checkout@v4

      # actions/setup-dotnet → встановлює .NET SDK потрібної версії
      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '8.0.x'   # встановить останній патч .NET 8

      - name: Restore dependencies
        run: dotnet restore   # аналог script: у GitLab

      - name: Build
        run: dotnet build --configuration Release --no-restore

      # actions/upload-artifact → зберегти файли (аналог artifacts: у GitLab)
      - name: Upload build artifacts
        uses: actions/upload-artifact@v4
        with:
          name: build-output
          path: |
            api/bin/
            api/obj/
          retention-days: 1   # зберігати 1 день

  # ── Job: test ───────────────────────────────────────────────────────────
  test:
    runs-on: ubuntu-latest
    # needs: → цей job чекає завершення "build" (аналог stage: після попереднього stage)
    needs: build

    steps:
      - uses: actions/checkout@v4

      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '8.0.x'

      # actions/download-artifact → завантажити artifacts від job "build"
      - name: Download build artifacts
        uses: actions/download-artifact@v4
        with:
          name: build-output

      - name: Run tests
        run: dotnet test --configuration Release --no-build --verbosity normal

  # ── Job: docker ─────────────────────────────────────────────────────────
  docker:
    runs-on: ubuntu-latest
    needs: test   # запускати після успішного test

    steps:
      - uses: actions/checkout@v4

      # Docker вже встановлений на ubuntu-latest — нічого додаткового не потрібно!
      # Це головна перевага GitHub Actions порівняно з GitLab + DinD
      - name: Build Docker image
        run: |
          docker build -t myapp:${{ github.sha }} .
          # ${{ github.sha }} → SHA коміту (аналог $CI_COMMIT_SHA у GitLab)
          docker images | grep myapp

  # ── Job: deploy ─────────────────────────────────────────────────────────
  deploy:
    runs-on: ubuntu-latest
    needs: docker
    # Запускати тільки для гілки main
    if: github.ref == 'refs/heads/main'

    steps:
      - uses: actions/checkout@v4

      - name: Deploy to staging
        run: |
          echo "Branch: ${{ github.ref_name }}"
          echo "Commit: ${{ github.sha }}"
          echo "Run ID: ${{ github.run_id }}"
          echo "Deployment: SIMULATED OK"
          # Тут буде реальна команда деплою (SSH, kubectl тощо)

5.3 Проблема синхронізації git.ztu.edu.ua і GitHub

Ідеальна ситуація: проект існує і на git.ztu.edu.ua (вимога університету) і на GitHub (для GitHub Actions, видимості, resume). Проблема — у поточній версії GitLab на git.ztu.edu.ua не працює pull mirroring (автоматичне підтягування змін з GitHub).

Є три підходи до вирішення:

Варіант A: git.ztu.edu.ua як основний репозиторій, GitHub як дзеркало

Ви ведете проект на git.ztu.edu.ua і використовуєте GitLab CI/CD. GitHub слугує дзеркалом — для публічного портфоліо або додаткових GitHub Actions. GitHub оновлюється автоматично при кожному push.

# ── Налаштування push mirror з GitLab на GitHub ──────────────────────────
# (Це робиться ОДИН РАЗ у налаштуваннях GitLab проекту)

# Крок 1: Створіть репозиторій на GitHub (порожній, без README)
# Наприклад: github.com/YOUR_USERNAME/diploma-project

# Крок 2: Створіть Personal Access Token на GitHub
# GitHub → Settings → Developer settings → Personal access tokens → Tokens (classic)
# Permissions потрібні: repo (повний доступ)
# Скопіюйте токен (він показується тільки один раз!)

# Крок 3: Налаштуйте mirror у GitLab
# git.ztu.edu.ua → ваш проект → Settings → Repository → Mirroring repositories
# → Add new mirror
#   Git repository URL: https://github.com/YOUR_USERNAME/diploma-project.git
#   Mirror direction: Push
#   Authentication method: Username and Password
#   Username: YOUR_GITHUB_USERNAME
#   Password: ghp_xxxxxxxxxxxxxxxx (ваш GitHub токен)
# → Mirror repository

# Після цього: кожен push у git.ztu.edu.ua автоматично відображається на GitHub!
# Перевірка: натисніть кнопку "Update now" і перевірте GitHub
Якщо push mirror недоступний у вашій версії GitLab на git.ztu.edu.ua: скористайтесь Варіантом B нижче — синхронізація через GitHub Actions.

Варіант B: Синхронізація GitLab → GitHub через GitHub Actions

Якщо push mirror у GitLab недоступний — GitHub Actions може сам підтягувати зміни з git.ztu.edu.ua за розкладом. Основний репозиторій залишається на git.ztu.edu.ua, GitHub оновлюється автоматично кожні 30 хвилин.

# .github/workflows/sync-from-gitlab.yml
# Цей workflow синхронізує GitHub ← git.ztu.edu.ua кожні 30 хвилин

name: Sync from GitLab

on:
  # schedule: запускати за розкладом (cron синтаксис)
  # "*/30 * * * *" → кожні 30 хвилин
  schedule:
    - cron: '*/30 * * * *'

  # workflow_dispatch: дозволяє запустити вручну через GitHub UI
  workflow_dispatch:

jobs:
  sync:
    runs-on: ubuntu-latest

    steps:
      - name: Sync from GitLab to GitHub
        run: |
          # Налаштування git
          git config --global user.email "sync-bot@example.com"
          git config --global user.name "Sync Bot"

          # Клонуємо з GitLab (git.ztu.edu.ua)
          # GITLAB_TOKEN — секрет який ви додасте у GitHub Secrets
          git clone --mirror \
            https://oauth2:${{ secrets.GITLAB_TOKEN }}@git.ztu.edu.ua/YOUR_USERNAME/diploma-project.git \
            repo/

          cd repo/

          # Відправляємо на GitHub
          # GITHUB_TOKEN — автоматично доступний у GitHub Actions
          git push --mirror \
            https://x-access-token:${{ secrets.GITHUB_TOKEN }}@github.com/YOUR_USERNAME/diploma-project.git
Як додати GITLAB_TOKEN у GitHub Secrets:
  1. Створіть Access Token на git.ztu.edu.ua: User Settings → Access Tokens → scope: read_repository
  2. GitHub → ваш репозиторій → Settings → Secrets and variables → Actions
  3. New repository secret → Name: GITLAB_TOKEN → Value: ваш токен

Варіант C: GitHub як основний репозиторій, дзеркало на git.ztu.edu.ua

Якщо студенту зручніше вести проект на GitHub і використовувати GitHub Actions — GitHub стає основним репозиторієм. git.ztu.edu.ua підтримується як дзеркало через налаштування git remote. CI/CD у цьому випадку налаштовується як GitHub Actions.

# Налаштування двох remote одночасно

# Ви вже маєте репозиторій на git.ztu.edu.ua:
git remote -v
# origin  https://git.ztu.edu.ua/YOUR/project.git (fetch)
# origin  https://git.ztu.edu.ua/YOUR/project.git (push)

# Додаємо GitHub як другий remote з назвою "github"
git remote add github https://github.com/YOUR_USERNAME/diploma-project.git

# Тепер у вас два remote:
# origin → git.ztu.edu.ua
# github → github.com

# Push в обидва репозиторії одночасно:
git push origin main    # → git.ztu.edu.ua
git push github main    # → GitHub

# АБО: налаштуйте один push у обидва remote одразу
git remote set-url --add --push origin https://git.ztu.edu.ua/YOUR/project.git
git remote set-url --add --push origin https://github.com/YOUR_USERNAME/diploma-project.git

# Тепер одна команда пушить в обидва:
git push origin main   # → git.ztu.edu.ua І GitHub одночасно

6. Реальний деплой для дипломного проекту

Живий застосунок за реальним URL — найсильніший аргумент на захисті. Якщо комісія може відкрити браузер і побачити що проект справді працює — це значно виразніше за будь-які скріншоти.

6.1 Загальні підходи до деплою

Незалежно від того яку платформу ви оберете для розгортання, підхід інтеграції з pipeline залишається однаковим. Платформи деплою зазвичай надають один з двох механізмів запуску:

  • Deploy Hook URL — унікальний URL, який при HTTP запиті запускає деплой на платформі
  • CLI інструмент — утиліта командного рядка яку можна встановити і викликати всередині CI job

6.2 Інтеграція деплою через Deploy Hook (GitLab CI/CD)

Якщо ваша платформа надає Deploy Hook URL — інтеграція зводиться до одного curl виклику у pipeline:

# .gitlab-ci.yml — деплой через Deploy Hook
deploy:
  stage: deploy
  tags: [student]
  only: [main]   # запускати тільки для основної гілки
  script:
    # DEPLOY_HOOK_URL — збережіть URL у GitLab CI/CD Variables
    # Settings → CI/CD → Variables → Add variable:
    #   Key:     DEPLOY_HOOK_URL
    #   Value:   https://platform.example.com/deploy/your-hook-url
    #   Protected: true  → доступна тільки для protected гілок (main)
    #   Masked:  true    → не відображати у логах pipeline

    # Надсилаємо HTTP запит щоб запустити деплой на платформі
    - curl -s "$DEPLOY_HOOK_URL"
    # -s → silent: не виводити прогрес, тільки відповідь

    - echo "Deploy triggered. Check your hosting platform for status."
  environment:
    name: staging
    url: https://your-app-url.example.com   # замініть на реальний URL

6.3 Інтеграція деплою через CLI (GitLab CI/CD)

Якщо платформа надає CLI інструмент — встановіть його всередині CI контейнера і викличте команду деплою:

# .gitlab-ci.yml — деплой через CLI платформи
deploy:
  stage: deploy
  image: alpine:latest   # мінімальний Linux image
  tags: [student]
  only: [main]
  before_script:
    # Встановити curl і необхідні утиліти
    - apk add --no-cache curl bash

    # Завантажити і встановити CLI вашої платформи
    # (замініть цей рядок на команду встановлення CLI вашої платформи)
    - curl -fsSL https://your-platform.com/install.sh | sh

    # Додати CLI до PATH якщо потрібно
    - export PATH="$HOME/.platform-cli/bin:$PATH"

  script:
    # PLATFORM_API_TOKEN — токен аутентифікації
    # Збережіть у GitLab Variables як PLATFORM_API_TOKEN
    # (Masked: true, Protected: true)
    - platform-cli deploy --token "$PLATFORM_API_TOKEN"
    # Замініть "platform-cli deploy" на реальну команду деплою вашої платформи

  environment:
    name: production
    url: https://your-app-url.example.com

6.4 Деплой через SSH на Linux сервер

Якщо у вас є доступ до будь-якого Linux сервера — це найбільш універсальний підхід який не залежить від конкретної платформи.

# .gitlab-ci.yml — деплой на Linux сервер через SSH
deploy_vps:
  stage: deploy
  image: alpine:latest
  tags: [student]
  only: [main]
  before_script:
    # Встановити SSH клієнт
    - apk add --no-cache openssh-client

    # Налаштувати SSH ключ
    # SSH_PRIVATE_KEY — приватний ключ збережений у GitLab Variables
    # Як створити ключ:
    #   ssh-keygen -t ed25519 -C "gitlab-deploy" -f deploy_key
    #   Приватний ключ (deploy_key) → у GitLab Variables як SSH_PRIVATE_KEY
    #   Публічний ключ (deploy_key.pub) → у ~/.ssh/authorized_keys на сервері
    - mkdir -p ~/.ssh
    - echo "$SSH_PRIVATE_KEY" > ~/.ssh/deploy_key
    - chmod 600 ~/.ssh/deploy_key   # SSH відмовить якщо права не 600

    # Вимкнути перевірку host key (для CI — прийнятно)
    - echo "StrictHostKeyChecking no" >> ~/.ssh/config

  script:
    # DEPLOY_HOST — IP або домен вашого сервера (у GitLab Variables)
    # DEPLOY_USER — ім'я користувача на сервері

    # Підключитись до сервера і виконати команди деплою
    - ssh -i ~/.ssh/deploy_key $DEPLOY_USER@$DEPLOY_HOST "
        # Зупинити поточний контейнер
        docker stop diploma-app 2>/dev/null || true
        docker rm diploma-app 2>/dev/null || true

        # Оновити код з репозиторію
        cd /opt/diploma-app
        git pull origin main

        # Перезібрати і запустити Docker контейнер
        docker build -t diploma-app:latest .
        docker run -d \
          --name diploma-app \
          --restart unless-stopped \
          -p 80:5000 \
          diploma-app:latest

        echo 'Deploy completed successfully'
      "
  environment:
    name: production
    url: http://$DEPLOY_HOST

7.2 Юніт-тести для .NET

// ── Тест для бізнес-логіки у .NET (xUnit) ─────────────────────────────
// xUnit — стандартний фреймворк тестування для .NET
// Встановлення: dotnet add package xunit

using Xunit;

namespace MyApp.Tests;

// Тестуємо клас який містить бізнес-логіку
// НЕ тестуємо контролери напряму — їх тестують інтеграційні тести
public class OrderServiceTests
{
    // [Fact] → звичайний тест без параметрів
    [Fact]
    public void CalculateTotal_WithDiscount_ReturnsCorrectTotal()
    {
        // ── Arrange: підготовка (що маємо на вході) ────────────────────

9. Моніторинг і логування

9.1 Структуровані логи замість Console.WriteLine

Console.WriteLine у production коді — ознака незрілого застосунку. Структуровані логи дозволяють фільтрувати, шукати і аналізувати події застосунку. Для комісії це демонстрація розуміння production-ready розробки.

Логування у .NET (вбудований ILogger)

// ── Правильне логування у ASP.NET Core ────────────────────────────────────
// ILogger<T> — вбудований інтерфейс логування .NET
// Не потребує додаткових пакетів

public class OrderService
{
    // Інжекція логера через конструктор (Dependency Injection)
    private readonly ILogger<OrderService> _logger;

    public OrderService(ILogger<OrderService> logger)
    {
        _logger = logger;
    }

    public Order CreateOrder(CreateOrderRequest request)
    {
        // LogInformation → рівень INFO: нормальні події застосунку
        _logger.LogInformation(
            "Creating order for user {UserId} with {ItemCount} items",
            request.UserId,   // структурований параметр (не string.Format!)
            request.Items.Count
        );

        try
        {
            var order = ProcessOrder(request);

            // LogInformation з результатом
            _logger.LogInformation(
                "Order {OrderId} created successfully. Total: {Total}",
                order.Id, order.Total
            );

            return order;
        }
        catch (InsufficientStockException ex)
        {
            // LogWarning → попередження: щось пішло не так але застосунок працює
            _logger.LogWarning(
                "Order creation failed for user {UserId}: insufficient stock for {ProductId}",
                request.UserId, ex.ProductId
            );
            throw;
        }
        catch (Exception ex)
        {
            // LogError → помилка: потрібна увага розробника
            _logger.LogError(
                ex,   // перший аргумент — exception для stack trace
                "Unexpected error creating order for user {UserId}",
                request.UserId
            );
            throw;
        }
    }
}

9.2 Health Check endpoint

Health check — спеціальний URL який повертає статус застосунку. Потрібен для моніторингу, load balancer-ів і демонстрації що застосунок «живий».

Health Check у ASP.NET Core

// Program.cs — додати health check у мінімальну конфігурацію
var builder = WebApplication.CreateBuilder(args);

// Реєструємо сервіс health check
builder.Services.AddHealthChecks()
    // Перевірка підключення до бази даних
    // Потрібен пакет: AspNetCore.HealthChecks.SqlServer або NpgSql
    .AddNpgSql(
        builder.Configuration.GetConnectionString("DefaultConnection")!,
        name: "database",
        tags: new[] { "db", "postgres" }
    );

var app = builder.Build();

// Маппінг endpoint-у health check
// GET /health → повертає 200 OK якщо все добре, 503 якщо є проблеми
app.MapHealthChecks("/health", new HealthCheckOptions
{
    // ResponseWriter → форматуємо відповідь як JSON
    ResponseWriter = async (context, report) =>
    {
        context.Response.ContentType = "application/json";
        var result = new
        {
            status = report.Status.ToString(),
            timestamp = DateTime.UtcNow,
            checks = report.Entries.Select(e => new
            {
                name = e.Key,
                status = e.Value.Status.ToString(),
                duration = e.Value.Duration.TotalMilliseconds
            })
        };
        await context.Response.WriteAsync(
            System.Text.Json.JsonSerializer.Serialize(result)
        );
    }
});

11.1 Як описати CI/CD у пояснювальній записці (по ДСТУ)

Пояснювальна записка до диплому має містити розділ де описані інструменти і процеси розробки. Нижче — рекомендована структура для опису CI/CD.

Рекомендована структура підрозділу

## X.Y Організація процесу розробки та автоматизації

### X.Y.1 Система контролю версій та репозиторій

Для управління версіями вихідного коду використовується система Git
з розміщенням репозиторію на університетській платформі git.ztu.edu.ua
(GitLab Community Edition).

Розробка ведеться за гілковою стратегією Feature Branch Workflow:
- гілка main — стабільна версія застосунку, що відповідає останньому
  розгорнутому релізу;
- гілка develop — поточна версія в розробці;
- гілки feature/* — окремі функціональні модулі.

### X.Y.2 Безперервна інтеграція (CI)

Для автоматизації процесу збірки та тестування реалізовано конвеєр
безперервної інтеграції засобами GitLab CI/CD. Конфігурація конвеєра
описана у файлі .gitlab-ci.yml у корені репозиторію.

Конвеєр складається з чотирьох послідовних етапів:

1. Етап build — відновлення залежностей та компіляція вихідного коду.
   Використовується офіційний образ mcr.microsoft.com/dotnet/sdk:8.0.

2. Етап test — запуск автоматизованих тестів. Реалізовано N юніт-тестів
   що перевіряють ключові модулі бізнес-логіки. Загальне покриття коду
   тестами складає X%.

3. Етап docker — збірка Docker-образу застосунку засобами
   Docker-in-Docker (DinD). Образ тегується ідентифікатором коміту
   для однозначної ідентифікації версії.

4. Етап deploy — автоматичне розгортання на тестовому сервері.
   Виконується лише для гілки main після успішного проходження
   попередніх етапів.

### X.Y.3 Контейнеризація

Застосунок упаковано у Docker-образ з використанням технології
багатоетапної збірки (multi-stage build). Це дозволило зменшити
розмір фінального образу з ~800 МБ (повний SDK) до ~200 МБ
(мінімальний runtime).

### X.Y.4 Якість коду

Для автоматичної перевірки якості коду виконується:
- статичний аналіз засобами [ESLint / flake8 / dotnet format];
- перевірка залежностей на наявність відомих вразливостей
  засобами [npm audit / pip-audit / dotnet list package --vulnerable];
- аналіз якості та покриття коду засобами SonarCloud.

11.4 Типові питання комісії та сильні відповіді

Питання комісіїСильна відповідь
Що таке CI/CD і навіщо це у вашому проекті? CI/CD — це автоматизований конвеєр який запускається при кожній зміні коду. У моєму проекті він автоматично перевіряє що код компілюється, тести проходять, і розгортає застосунок на сервер. Це виключає людський фактор і гарантує що у головній гілці завжди робочий код.
Чому обрали GitLab CI/CD, а не інший інструмент? Проект розміщений на git.ztu.edu.ua що є GitLab. Використання вбудованого CI/CD логічно — не потрібен окремий сервер, все в одному місці. Синтаксис .gitlab-ci.yml простий і декларативний. Для більш складних сценаріїв я також використав GitHub Actions для синхронізації репозиторіїв.
Що таке Docker і навіщо він тут? Docker дозволяє упакувати застосунок разом з усіма залежностями у контейнер. Це гарантує що застосунок однаково працює на моєму ноутбуці, на CI сервері і на production сервері. Також я використовую multi-stage build щоб зменшити розмір фінального образу з 800 МБ до 200 МБ.
Скільки тестів і яке покриття? У проекті N юніт-тестів і M інтеграційних тестів. Покриття коду складає X%. Юніт-тести перевіряють ключові методи бізнес-логіки [наведіть приклади]. Інтеграційні тести перевіряють основні API endpoints за допомогою WebApplicationFactory.
Що буде якщо тест впаде? Pipeline зупиниться на stage test і не перейде до deploy. На git.ztu.edu.ua з'явиться сповіщення і pipeline стане червоним. Застосунок не буде розгорнутий. Саме це і є головною метою CI — виявляти проблеми до того як вони потраплять до користувачів.
Як відбувається розгортання? При push у гілку main pipeline автоматично запускає deploy stage. Залежно від платформи розгортання — це може бути виклик Deploy Hook URL, виклик CLI інструменту платформи, або SSH команди на сервер. Після деплою pipeline може перевіряти health check endpoint щоб переконатись що застосунок запустився коректно.
Що таке артефакти pipeline? Артефакти — це файли що зберігаються після виконання job і можуть використовуватись у наступних stages. У моєму pipeline stage build зберігає скомпільовані файли, stage test зберігає HTML звіт покриття тестами. Їх можна завантажити прямо з інтерфейсу GitLab.
Чому runner запущений локально? Це не ненадійно? Для дипломного проекту це прийнятне рішення — runner запускається на моєму ноутбуці під час розробки. У production середовищі runner розміщується на окремому сервері який працює постійно. Для GitHub Actions використовуються hosted runners Microsoft що не залежать від моєї машини.

11.5 Скріншоти для пояснювальної записки

Вставте у розділ «Реалізація» або «Тестування» такі скріншоти:

  1. Список pipeline-ів — CI/CD → Pipelines. Має бути видно що останні pipeline зелені.
  2. Деталі pipeline — відкрийте один pipeline і покажіть всі 4 stages зеленими.
  3. Лог тестів — відкрийте job test і зробіть скріншот рядку «Passed! - N tests».
  4. Coverage звіт — HTML звіт з відсотком покриття і списком файлів.
  5. SonarCloud дашборд (якщо налаштовано) — якість коду, кількість issues.
  6. Живий застосунок — браузер з URL вашого deployed застосунку (якщо є).
  7. README з бейджами — скріншот README де видно зелені бейджі.
Порада щодо скріншотів: робіть скріншоти у момент коли все зелене і pipeline тільки що завершився. Дата і час на скріншоті мають бути актуальними — комісія може звернути на це увагу.
